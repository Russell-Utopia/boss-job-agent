# Web 技术栈对比原型

这是 GitHub 工单“用复杂交互原型验证 Web 技术栈”的可丢弃证据，不是生产实现。

本目录是独立 Go Module，不属于根应用 Module，也不进入根目录 `make check`。

它只回答一个问题：在相同业务结果、视觉和操作脚本下，Go 服务端页面与 React + TypeScript + Vite 哪一种更适合继续实现 MVP Web。

## 固定比较范围

- 岗位侧使用“加入模拟队列”，不使用或解释“重新鉴定”。
- 共享内存场景提供八条平台岗位、动作资格、禁用原因和一次提交时状态变化。
- 策略候选稿由固定结果模拟生成，只保存在当前浏览器页面内存。
- 不访问 SQLite、BOSS 或 Pi，不产生真实首次沟通。
- 两套表现层共享业务场景和 CSS，但不共享浏览器状态代码。

## 启动

在仓库根目录运行：

```bash
./throwaway-prototypes/web-stack-comparison/run.sh
```

首次启动会在原型目录内安装 React 构建依赖。启动后打开：

- Go 服务端页面：<http://127.0.0.1:8091/prototype/go/jobs>
- React：<http://127.0.0.1:8091/prototype/react/?page=jobs>

页面底部可以切换技术栈并重置共享场景。

## 当前结论

MVP Web 选择 Go 服务端页面，复杂但只属于当前浏览器会话的交互使用少量原生 JavaScript 补足。

依据：

- 实际操作中，两套原型的筛选、批量提交、提交时重新校验、候选稿编辑和实时 diff 没有表现出明显的体验差距。
- 当前 Web 和应用模块已经运行在同一个 Go 进程。服务端页面可以直接使用应用接口并复用业务拒绝结果，不需要为每个页面状态再维护一层 JSON 映射。
- React 方案还要维护客户端异步状态、前后端类型对应、JSON 接口、Node 依赖和独立构建产物；当前场景没有得到足以抵消这部分成本的交互收益。

如果以后主要页面变成长时间不换页、包含大量客户端组合状态的工作台，或者同一套 Web 接口需要服务多个独立客户端，再重新评估 React；这不是当前 MVP 的前提。

## 同一操作脚本

每套原型开始前先“重置共享场景”，然后执行：

1. 搜索 `Go`，平台状态选择“可沟通”，应用筛选。
2. 点击“全选当前可处理记录”，观察不可处理记录旁的业务原因。
3. 提交“加入模拟队列”。`J-1002` 会在提交时模拟状态变化，结果应同时显示成功和跳过原因。
4. 进入“岗位鉴定”，生成策略候选稿。
5. 修改候选稿任意一行，确认逐行 diff 立即变化且没有额外模型调用。
6. 在未丢弃候选稿时点击页面导航或技术栈切换：取消提醒应留在当前页面，确认后才离开；关闭或刷新页面仍由浏览器提供兜底提醒。
7. 丢弃候选稿，确认页面回到“尚未生成”。

完成后只比较操作感受、状态正确性、实现复杂度、测试面和构建成本；这组样例不代表完整产品流程。
