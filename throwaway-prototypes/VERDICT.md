# THROWAWAY PROTOTYPE：已收敛为 Web

用户已明确选择 Web，并否定旧的控制台、台账和泳道三套布局。旧布局的问题不是配色或密度，而是把运行监控、岗位处理、批量动作和自动化设置摊在同一层，让用户无法建立稳定主线。

当前原型只保留一个信息架构：

1. **岗位**是默认工作面：顶部三块表牌统一使用“已完成 / 总数 + 进度条”；下方分页列表同时承载状态筛选、单岗位直接操作和批量处理，并允许选择每页 10 / 20 / 50 / 100 条。
2. 不再保留独立的**执行情况**入口。三块运行概况和岗位列表在同一个注意力路径中，概况里的“筛出”直接作用于下方列表。
3. 左侧导航按用户目的拆为**岗位、岗位鉴定、首次沟通、在线简历**，不再用横向顶栏营造 Demo 式切页。
4. **岗位鉴定**页首只保留一个“生成新策略”，候选稿用本地逐行 diff 直接标出删除与新增，按钮简化为取消、重新生成和采用策略；“AI 同时鉴定数”直接输入正整数，5 只是首次默认值。**首次沟通**通过弹窗选择预设或自定义起止时间，空时间窗仍表示全天可发送。

岗位表将“AI 鉴定”和“人工结论”分成两列。人工列直接呈现未复核、已复核的适合/不适合以及 JD 变化后的待重新复核，并提供对应筛选；每行直接展示人工复核、重新鉴定、模拟沟通和真实发送，禁用按钮通过悬停解释原因，批量模式不再是单条操作的前置步骤。

这个结构同时避免了一个领域误解：岗位发现是单个可恢复运行；鉴定与首次沟通是平台岗位上的执行状态，三者不能被包装成同一种“任务”。界面只显示“尚未安排、等待开始、处理中、已有结论”等用户能直接行动的状态，不暴露内部调度术语。

在线简历页是唯一手工刷新入口；发现和鉴定都不会自行访问 BOSS。一轮发现固定使用开始时的在线简历版本，暂停恢复不切换；新版本只用于下一次发现。岗位发现不绑定鉴定策略；安排鉴定只表示等待开始。Worker 真正开始鉴定时独立采用数据库中最后一次手工保存的在线简历版本、届时当前策略和岗位 JD，所以它可以在发现仍使用 v1 时使用 v2。已开始的鉴定不会中途切换。默认策略 v1 只属于岗位鉴定模块。

在线简历或策略版本更新不会使历史岗位的最新有效人机结论失效。开启自动首次沟通就是持续授权当前全部有效“适合”结论参与自动安排，不触发全库重鉴定、撤回、二次确认或额外阻断；实际使用版本仍保留用于追溯。

同理，新发现运行使用 v2 只决定搜索范围，不代表重复岗位都已用 v2 鉴定。已有岗位 JD 判断内容未变时继续复用基于 v1 的最新有效结论和发送资格，并在详情里保留 v1 追溯信息；无结论、JD 判断内容变化或用户明确重新鉴定时才安排新的鉴定。

人工复核覆盖 AI“适合”“不适合”和“需要人工确认”，也允许再次覆盖旧人工结论；“建议人工确认”只是注意力筛选，不是复核资格。人工可以连续复核任意数量岗位，期间 0 次 LLM；只有用户在岗位鉴定页显式点击“生成新策略”时才模拟 1 次模型调用，并输入生成当时的当前策略及当时全部仍对应当前 JD 的人工正负标注，返回一份完整、可编辑候选稿。候选稿只存在于当前页面会话；关闭、取消、离开或重新生成前必须确认永久丢失，重新打开和后台重启都不能恢复。用户采用编辑后的完整文本时才创建并启用新正式版本；原型不保存候选稿或处理历史，也不暗示新增候选稿业务表。

人工复核界面必须同时展示当前 JD 快照的岗位基本信息、完整工作职责和任职要求，以及 AI 结论、理由和实际使用版本；人工判断按钮固定在弹窗底部，不能要求用户仅根据 AI 摘要盲审。

全局岗位只按稳定 `platform_job_id` 去重；再次发现相同岗位复用同一条 `assessment_status` 与 `outreach_status`。已有结论不因重复发现再次鉴定，已真实沟通岗位保留原判断但不再进入鉴定或发送处理。平台关闭、稳定 ID 缺失和已真实沟通只影响处理资格，不参与适合性结论。
