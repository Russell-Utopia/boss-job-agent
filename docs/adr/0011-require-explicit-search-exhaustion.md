# 在岗位发现运行中保存唯一搜索检查点

BOSS 搜索界面表现为下拉加载，但可靠列表读取具有明确页码并返回显式 `HasMore`。因此 `discovery.Service` 可以在登录中断或后端重启后直接核对尚未完成的页，不必重新加载之前的全部页面；页面端点、请求参数、Cookie、会话材料和浏览器执行类型仍由可替换的生产 Adapter 封装。

每个 `discovery_runs` 直接保存当前意向岗位、目标城市、当前页码，以及当前页的有序稳定岗位 ID、显式 `HasMore` 和下一个尚未完成的岗位序号，不建立 `search_progress` 或“运行拥有岗位”的关系表。`discovery.Service` 先用 `ListPage` 冻结页内清单，再严格按顺序调用 `ReadJob`；每个可靠岗位必须先经 `JobPool.Observe` 插入或更新全局 `platform_jobs`，成功后才能推进岗位序号。进程在两次写入之间中断时，恢复最多重读当前一个岗位，并依靠稳定 `platform_job_id` 幂等更新，不重放更早的岗位。

恢复已有页内检查点时必须再次调用 `ListPage`，并完整核对有序 ID 和 `HasMore`。列表变化属于 `invalid_response`，保留原检查点并等待求职者处理，不拼接新旧列表、不跳过岗位。单条岗位的 JD 内容读取失败（例如详情页残缺、反爬导致 JD 为空）与列表完整性 `invalid_response` 属于不同的错误类：它是**单岗位可重试读取失败**（等同登录墙、超时、残页），走既有的单岗位重试与退避，绝不单独把整个 run 判为 `invalid_response`；JD 内容本身永不构成列表耗尽或列表完整性信号。只有页内全部岗位完成后，才能同时清除页内检查点并推进页码、切换搜索范围或完成运行。岗位观察先在一个短 SQLite 事务中锁定并校验运行 ID、`attempt_no`、Worker owner、搜索范围、页码和岗位序号，再通过 `JobPool` 自己的查询写入全局岗位池；事务提交后才用同一组当前性条件推进 checkpoint。这样跨进程暂停或新尝试不能插入“校验通过、岗位尚未写入”的窗口，事务提交与 checkpoint 推进之间仍保留可恢复的单岗位重读窗口。

当前搜索范围只有明确取得 `HasMore=false` 且完成该页全部岗位后，才能切换到本次记录的在线简历版本中的下一个搜索范围并把页码重置为 1。全部搜索范围耗尽后，运行进入 `completed`；空 DOM、连续无新增岗位、达到读取上限、请求超时、重复返回、页面异常或无法读取终止信号都不能证明耗尽，这些执行错误只把运行写入 `failed`，技术细节进入持久化结构化运行日志。Web 关闭不改变运行状态；后端 Worker 仍持有有效租约时继续搜索，租约过期则在后端重启时把运行标为失败，由求职者重试原运行或明确提前结束。v1 同时最多只有一个准备中、运行中、暂停中或失败待处理的岗位发现运行；当前运行完成或提前结束后即可开始新运行，不要求全局鉴定或打招呼队列已经收口。

发现运行每次开始或恢复执行时递增生命周期内单调递增的 `attempt_no`；该字段不直接充当重试上限。`consecutive_failure_count` 记录当前无人干预执行周期的连续失败次数，自动重试开始时不归零，只有完成准备、成功推进页内岗位或页面检查点，或求职者显式重新开始后才归零。临时网络或页面错误写入 `failed` 和有限退避后的 `retry_at`；`discovery.Service` 启动时及之后每分钟执行一轮调度，发现到期运行后恢复同一运行并重试当前检查点。长页中每个清单或岗位读取完成后以当时的新鲜时间写进度并续租，不能让整页复用扫描开始时间而在仍推进时过期。v1 默认一个无人干预周期总共最多尝试三次（包含首次）：第一次和第二次失败可安排自动重试，第三次失败后 `retry_at` 为空；登录失效、验证码和平台限制等不可自动恢复错误从第一次失败起就不安排重试。`ListPage` 与每个 `ReadJob` 分别记录 started/finished runlog；岗位读取只记录页码、页内序号和稳定 ID 指纹，不保存请求、响应或原始稳定 ID。
