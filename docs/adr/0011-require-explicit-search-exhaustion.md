# 在岗位发现运行中保存唯一搜索检查点

BOSS 搜索界面表现为下拉加载，但当前列表请求具有明确的 `page`、`pageSize` 参数，响应包含 `hasMore`。因此 `SearchService` 可以在登录中断或后端重启后直接请求尚未完成的页，不必重新加载之前的全部页面；页码访问仍由可替换的浏览器执行器封装。

每个 `discovery_runs` 直接保存当前意向岗位、目标城市和下一页页码，不再建立一对一的 `search_progress` 表。只有一页中的全部稳定平台岗位及其可靠的“可沟通/已关闭”证据都已插入或更新到 `platform_jobs`，才能递增下一页；单个岗位的 JD 或平台状态读取失败时，发现运行直接写入 `failed`，技术细节写入持久化结构化运行日志，页码保持不变，不为岗位写入第三种未知状态。求职者或自动重试恢复同一运行后重新读取该页，相同 `platform_job_id` 依靠全局唯一约束去重。

当前搜索范围明确取得 `hasMore=false` 后，同一运行切换到本次记录的在线简历版本中的下一个搜索范围并把页码重置为 1。全部搜索范围耗尽后，运行进入 `completed`；连续无新增岗位、请求超时、重复返回、页面异常或无法读取终止信号都不能证明耗尽，这些执行错误只把运行写入 `failed`，技术细节进入持久化结构化运行日志。Web 关闭不改变运行状态；后端 Worker 仍持有有效租约时继续搜索，租约过期则在后端重启时把运行标为失败，由求职者重试原运行或明确提前结束。v1 同时最多只有一个准备中、运行中、暂停中或失败待处理的岗位发现运行；当前运行完成或提前结束后即可开始新运行，不要求全局鉴定或发送队列已经收口。

发现运行每次开始或恢复执行时递增生命周期内单调递增的 `attempt_no`；该字段不直接充当重试上限。`consecutive_failure_count` 记录当前无人干预执行周期的连续失败次数，自动重试开始时不归零，只有完成准备、成功推进搜索检查点或求职者显式重新开始后才归零。临时网络或页面错误写入 `failed` 和有限退避后的 `retry_at`；`SearchService` 启动时及之后每分钟执行一轮调度，发现到期运行后恢复同一运行并重试当前检查点。v1 默认一个无人干预周期总共最多尝试三次（包含首次）：第一次和第二次失败可安排自动重试，第三次失败后 `retry_at` 为空；登录失效、验证码和平台限制等不可自动恢复错误从第一次失败起就不安排重试。每次错误都先更新当前业务状态再决定何时重试；详细技术错误写入带 trace ID、发现运行 ID 和尝试号的持久化结构化日志，不增加业务错误字段或历史业务表。
