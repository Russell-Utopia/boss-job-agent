# 同一岗位真实打招呼成功后不再重复

一旦某个 `platform_job_id` 被确认成功完成首次打招呼，`platform_jobs.outreach_status` 永久记为 `contacted`，不按岗位发现运行或日期重置；以后再次发现该岗位只更新可展示的当前 JD 和最后发现时间，不重新进入打招呼队列。如果 SQLite 没有记录但 BOSS 显示此前已经打过招呼，也以 BOSS 的外部状态为准停止动作并补记全局岗位状态。只有招聘方重新发布并产生新的平台岗位 ID 时，才视为新的平台岗位。

“已经真实打过招呼的岗位不再重复”由 `JobPool` 的本地打招呼资格检查和 `PostService` 的 BOSS 动作前复查共同保证，而不是交给 LLM 或单个 Worker 自行判断。平台岗位入队和 Worker 领取由 `JobPool` 重新检查本地全局状态，只有最近一次可靠平台岗位状态为“可沟通”才允许继续；真实打招呼前，`PostService` 还要读取 BOSS 当前状态，发现岗位已关闭或 `contact=true` 时停止动作，并把证据提交给 `JobPool` 更新平台岗位状态或补记已打招呼事实。若检查在外部动作发生前失败，则保留最近一次可靠平台岗位状态，由 `JobPool` 把状态写为 `failed`；只有动作可能已经发生但结果无法确认时才写为 `possibly_contacted`，在对账前禁止重试。并发、恢复或批量选择都不能绕过这两层检查。

正常打招呼取得 BOSS 成功证据后，`PostService` 在同一次处理里把证据提交给 `JobPool`，由后者自动把岗位从 `processing` 推进为 `contacted`，保存时间、来源和页面证据，不经过 `possibly_contacted`。只有点击或请求可能已经到达 BOSS、但程序在取得确认或写入本地结果前发生超时、断线或崩溃时，才进入 `possibly_contacted`。恢复后 `PostService` 优先自动对账并把证据提交给 `JobPool`：BOSS 证明已打招呼则推进为 `contacted`，可靠证明未打招呼则推进为 `failed`，仍无法取得证据则保持 `possibly_contacted`；任何情况下都不能直接从该状态重新打招呼。

每次打招呼尝试开始前递增生命周期内单调递增的 `outreach_attempt_no` 并把状态写为 `processing`。能够确认没有产生打招呼的错误写为 `failed` 并递增 `outreach_consecutive_failure_count`；临时错误只有在连续失败次数尚未达到程序配置上限时才设置有限退避后的 `outreach_retry_at`。`PostService` 启动时及之后每分钟执行一轮调度，把已经到期的打招呼工作恢复为可领取状态；普通工作和到期工作之后走同一个领取路径，不为每个岗位创建计时器。v1 默认一个无人干预周期总共最多尝试三次（包含首次）；确认成功或求职者处理后显式重新开始时才归零。登录失效、验证码和平台限制等不可自动恢复错误从第一次失败起就不安排自动重试。`possibly_contacted` 在对账确认没有打招呼并转为 `failed` 前不计为明确失败。详细技术错误写入持久化结构化运行日志，以 trace ID、平台岗位 ID 和尝试号检索；业务表只保存状态、失败次数、重试时间和外部证据。鉴定与打招呼分别保存失败次数和重试时间，不能共用字段，也不共享通用重试接口。
