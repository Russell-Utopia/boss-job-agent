# 通过 Pi RPC 推送鉴定并使用单个 MCP 工具确认结果

Go 程序确定性地拥有岗位发现运行、`platform_jobs` 上的全局鉴定与打招呼逻辑队列、平台岗位开放与已打招呼门禁、租约、重试和恢复。v1 的鉴定执行器采用 Pi：自动或手工入队都只把符合条件的 `not_queued` 岗位改为 `pending`，不选择简历或策略；无论自动开关是否开启，`AdviceService` 都继续消费已经入队的岗位。每次准备调用 Agent 时，它只读取数据库中用户手动保存的当前在线简历版本、用户设置中启用的策略和当前鉴定器版本，并显式传给 `JobPool.ClaimAssessments`，不得访问 BOSS 自动刷新。领取事务把少量 `pending` 改为 `processing`，记录届时当前 JD 及实际采用的版本、递增尝试次数并建立租约，且全局 `processing` 岗位数不得超过“同时鉴定岗位上限”。随后主动推送完整在线简历、完整 JD、完整策略、平台岗位本地主键和当前尝试次数，Agent 不只接收内部 ID，也不读取 `discovery_runs`。已关闭或已确认打招呼的岗位不调用 Pi；Pi 不拥有队列，也不主动领取工作。

Pi 只获得一个回调能力 `confirm_assessment_results`；该工具为一个或多个岗位分别提交平台岗位本地主键、鉴定尝试次数、三态结论、理由和证据。`AdviceService` 校验协议后把各项结果交给 `JobPool.FinishAssessments`；`JobPool` 只接受平台岗位仍处于鉴定处理中且尝试次数完全一致的结果，有效结果覆盖该岗位的当前 AI 结论并递增鉴定版本。岗位在推送后关闭时，已经发生的模型调用不再节省，符合尝试号和输入依据的有效结果仍可落库供重新开放后复用，但不得因此进入打招呼队列。迟到回调因尝试次数不匹配而被拒绝，某项格式错误或缺失只影响该项，其余有效结果仍然落库。普通模型文本不改变业务状态。

系统不为 Go 与 Pi 的交互建立鉴定运行、鉴定批次、批次明细或独立鉴定结果表，也不保存组合输入指纹或逐次 AI 历史；平台岗位自身保存当前鉴定的领取、生命周期内单调递增的 `assessment_attempt_no`、当前执行周期的 `assessment_consecutive_failure_count`、重试时间、实际输入依据和结果。Pi 结束、超时或中断但没有有效确认时，岗位写入 `assessment_status=failed` 并递增连续失败次数；临时错误只有在次数尚未达到程序配置上限时才设置有限退避后的 `assessment_retry_at`。`AdviceService` 启动时及之后每分钟执行一轮调度；到期岗位仍保持 `failed`，由下一次领取直接使用届时当前输入进入 `processing`：输入未变化就延续失败次数，输入变化则开启新的失败周期。v1 默认一个无人干预周期总共最多尝试三次（包含首次）；有效结果落库或求职者显式重新开始后才把连续失败次数归零。详细技术错误写入带 trace ID、平台岗位 ID 和尝试号的持久化结构化日志，不建立业务错误字段或历史业务表。鉴定与打招呼各自保存失败次数和重试时间，互不阻塞，也不共享通用重试接口。未来可以替换 Pi 或改为直接模型调用，但不能改变“程序推送、单一确认回调、平台岗位为结果所有者”的接口。Pi 进程和会话生命周期遵循 ADR-0015。
