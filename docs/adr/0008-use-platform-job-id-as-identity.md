# 以 BOSS 平台岗位 ID 作为岗位身份

产品以 BOSS 返回的 `encryptJobId` 作为 `platform_job_id`，并保存 `/job_detail/{encryptJobId}.html` 形式的 canonical URL。SQLite 的 `platform_jobs` 保证一个 BOSS 岗位只有一条全局记录；不同岗位发现运行和搜索范围再次看到相同平台 ID 时，只更新这条记录的当前岗位事实和最后发现时间，不建立运行与岗位关联表。JD 判断内容未变化时继续保留原鉴定，不因新运行使用了不同简历版本而再次进入鉴定；只有 JD 判断内容变化或缺少当前有效结论时才进入新的鉴定。当前 AI 鉴定、最新人工结论、打招呼队列状态和永久已打招呼事实都由这条平台岗位记录持有；岗位判断内容变化后，旧人工结论仍留在该岗位上，但因为所依据的 JD 哈希不再匹配而转为待复核。无法取得稳定 ID 的 JD 可以写普通运行日志供排查，但不得进入全局岗位池或打招呼队列，避免仅凭岗位名、公司名等易冲突字段向错误目标发送消息。

`jd_hash` 对规范化后的岗位判断内容计算，而不是对抓取到的原始 JSON 字节计算。哈希输入包含岗位名称、公司、城市、薪资、完整 JD 文本（不再区分职责与要求）；JSON 对象键顺序、换行差异、无意义首尾空白、页面排版、抓取时间、展示元数据和招聘状态不参与计算。这样只有可能改变求职者适合性判断的内容才会使 AI 结论失效或把人工结论转为待复核，页面格式抖动不会制造无意义的重复鉴定。

招聘状态作为同一条 `platform_jobs` 记录上的独立当前事实保存为“可沟通”或“已关闭”，同时保存最近一次可靠证据的时间；已关闭时还保存用户可见原因。页面读取失败是 `SearchService` 或 `PostService` 的操作错误，不是岗位本体的第三种状态，也不会覆盖最近一次可靠事实。明确已关闭时不发起新的 AI 鉴定，尚未领取的打招呼请求必须撤回；已有 AI 和人工结论继续保留。岗位重新开放且 `jd_hash` 未变化时可以继续复用原结论；如果原本没有有效结论，保留的待鉴定状态会重新取得领取资格。
