# 以 BOSS 平台岗位 ID 作为岗位身份

产品以 BOSS 返回的 `encryptJobId` 作为 `platform_job_id`，并保存 `/job_detail/{encryptJobId}.html` 形式的 canonical URL。SQLite 的 `platform_jobs` 保证一个 BOSS 岗位只有一条全局记录；不同岗位发现运行和搜索范围再次看到相同平台 ID 时，只更新这条记录的当前岗位事实和最后发现时间，不建立运行与岗位关联表。JD 判断内容未变化时继续保留原鉴定，不因新运行使用了不同简历版本而重新鉴定；未沟通岗位的 JD 判断内容变化后清除旧 AI 结论，旧人工结论仍留在该岗位上，但因为所依据的 JD 哈希不再匹配而转为待复核。已经确认沟通的岗位不再进入鉴定或发送流程，因此 JD 后来变化时继续保留当时的 AI 与人工结论供查看。无法取得稳定 ID 的 JD 可以写普通运行日志供排查，但不得进入全局岗位池或发送队列，避免仅凭岗位名、公司名等易冲突字段向错误目标发送消息。

同一公司重新发布文字相同或相似的 JD，只要 BOSS 产生新的 `platform_job_id`，就作为新的平台岗位写入独立记录。新岗位不继承旧岗位的 AI 结论、人工结论、鉴定队列状态或沟通状态；即使两者 `jd_hash` 完全相同，也不会跨记录复用。这样可能再次鉴定并联系同一公司的相似岗位，但避免把新招聘名额、新招聘者或重新开放的机会误合并；如果以后需要提示相似岗位，应作为独立提示能力，而不是改变平台岗位身份。

`jd_hash` 对规范化后的岗位判断内容计算，而不是对抓取到的原始 JSON 字节计算。哈希输入包含岗位名称、公司、城市、薪资、职责和要求；JSON 对象键顺序、换行差异、无意义首尾空白、页面排版、抓取时间、展示元数据和招聘状态不参与计算。它只用于判断同一 `platform_job_id` 的内容是否变化，不是跨岗位身份或去重键；这样只有同一岗位中可能改变求职者适合性判断的内容才会使 AI 结论失效或把人工结论转为待复核，页面格式抖动不会制造无意义的重复鉴定。

招聘状态作为同一条 `platform_jobs` 记录上的独立当前事实保存为“可沟通”或“已关闭”，同时保存最近一次可靠证据的时间；已关闭时还保存用户可见原因。页面读取失败是 `SearchService` 或 `PostService` 的操作错误，不是岗位本体的第三种状态，也不会覆盖最近一次可靠事实。明确已关闭时不发起新的 AI 鉴定，尚未领取的发送请求必须撤回；已有 AI 和人工结论继续保留。岗位重新开放且 `jd_hash` 未变化时可以继续复用原结论；如果原本没有有效结论，保留的待鉴定状态会重新取得领取资格。
