# 以全局岗位池解耦岗位发现、鉴定和首次沟通

用户真正管理的是全局岗位，而不是一次运行下的岗位清单。因此删除 `task_jobs`，不再持久化“某次运行发现或采用过哪些岗位”的关联；这类信息既不参与用户判断、恢复、避免重复打招呼或全局展示，必要时只写普通运行日志。每个稳定 `platform_job_id` 在 `platform_jobs` 中只有一条记录，当前 JD、平台岗位状态、当前 AI 鉴定、最新人工结论、全局鉴定与发送队列状态以及是否已经真实沟通都由它持有。该决定取代 ADR-0013，并修正 ADR-0006、ADR-0008 和 ADR-0012 中由 `task_jobs` 拥有推进状态的部分。

原 `communication_tasks` 收缩并改为用户可见的 `discovery_runs`。岗位发现运行只保存用于搜索的在线简历版本 ID、当前搜索范围、下一页、状态、失败或暂停原因、生命周期尝试编号、当前连续失败次数、重试时间和发现 Worker 租约；在线简历版本首次记录后不可修改，整轮所有搜索范围以及暂停后的恢复都使用同一版本。运行期间手动刷新产生的新版本不会同步到本轮；要用新版本重新初筛，必须在本轮完成或提前结束后创建新运行。岗位发现不会访问 BOSS 自动刷新简历，也不保存或选择岗位鉴定策略，搜索检查点直接并入该记录，不再建立 `search_progress`。它不拥有所发现的平台岗位，也不等待鉴定或发送队列收口。TUI 或 Web 关闭不改变运行状态；后端仍持有有效租约时继续搜索，后端中断则在租约过期后写入 `failed` 和具体错误。v1 同时最多存在一个准备中、运行中、暂停中或失败待处理的岗位发现运行，用户必须继续它，或明确提前结束后才能创建新运行；当前运行完成或提前结束后，即使全局鉴定或发送仍在处理，也允许创建新运行。

`SearchService` 只推进岗位发现运行，并把本轮取得的可靠岗位观察提交给 `JobPool`；它不会直接更新 `platform_jobs`、刷新在线简历、选择鉴定策略或在新运行开始时扫描全部历史岗位。`JobPool` 是 `platform_jobs` 的唯一写入模块，负责在一个事务中完成 JD 更新、平台开放状态、因 JD 变化导致的鉴定失效、人工结论、队列资格和“已经真实沟通过后不再重复鉴定或打招呼”规则的关联变化。新运行再次发现已有岗位且 JD 判断内容未变化时，只刷新同一条平台岗位的事实和最近发现时间，既有鉴定及沟通状态继续复用；运行使用了新的在线简历版本本身不是重新鉴定指令。缺少有效结论的岗位先进入 `not_queued`；`AdviceService` 只在自动岗位鉴定开启时接收新工作为 `pending`，但始终继续消费已经排队的岗位。它在把岗位领取为 `processing` 时才读取并记录用户最后一次手动保存的当前在线简历版本、用户设置策略、JD 和鉴定器版本，因此手动刷新或设置变化会影响尚未开始的待鉴定岗位，不改变已经开始的鉴定。`PostService` 同样只在自动首次沟通开启时接收新的合适岗位，已经入队的真实发送则在首次沟通时间窗内继续消费，可能已沟通的对账不受时间窗限制。已关闭或已经确认沟通的岗位不再进入新的鉴定或发送工作；已有 AI 和人工结论继续保留。发现、鉴定和发送分别保存自己的生命周期尝试编号、当前连续失败次数、失败原因和重试时间，不共享退避控制；v1 每个无人干预执行周期默认总共最多尝试三次（含首次）。页面读取失败由正在执行的流程写入自己的 `failed`，不产生平台岗位第三状态，只有发送动作可能已经产生外部影响时使用 `possibly_contacted`。用户在全局岗位列表中查看是否适合、是否已沟通及未沟通原因，也可以显式批量加入或重新加入鉴定队列，或把符合条件的岗位加入模拟队列或真实发送队列；内部简历 ID 和策略版本不需要用户选择。发现运行完成只表示搜索范围已经耗尽，全局鉴定与发送可以继续独立推进。
