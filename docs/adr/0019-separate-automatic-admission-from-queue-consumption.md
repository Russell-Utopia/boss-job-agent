# 将自动入队开关与已有队列消费分开

自动岗位鉴定和自动打招呼都只控制“是否把新的符合条件岗位自动加入对应队列”，不作为执行模块的启停开关；关闭后，已经入队、正在处理或仍在自动重试周期内的工作继续完成，求职者显式批量加入的工作也不受自动开关限制。鉴定入队只把符合条件的 `not_queued` 岗位改为 `pending`，不读取或记录简历、策略版本和鉴定器；`AdviceService` 按并发上限把少量 `pending` 领取为 `processing` 时，只读取数据库中用户最后一次手动保存的当前在线简历版本，并记录该版本、用户设置策略、当前 JD 和鉴定器版本，不得访问 BOSS 自动刷新。这样 `pending` 只表示已经排队，不代表已经推给 Pi 或开始执行；用户手动刷新的简历版本或策略设置变化会被尚未开始的待鉴定岗位采用，但不修改已经 `processing` 的输入。

岗位鉴定按可配置的“同时鉴定岗位上限”限制 `processing` 岗位数，调低上限不打断在途工作。鉴定得到 `suitable` 只形成打招呼资格，不直接把打招呼状态改为 `pending`；只有自动打招呼仍开启或求职者手工批量加入时才进入打招呼队列。开启自动打招呼是求职者对当前全部有效人机结论的持续授权，不要求已有 AI 结论采用后来保存的当前简历或策略版本，也不因这些版本变化撤回待打招呼工作。未设置打招呼时间窗时可以全天领取新的真实打招呼；设置后才在区间外停止领取，区间结束时已经开始的动作继续收尾，可能已打招呼的只读对账始终可以执行。关闭自动打招呼不撤回已有 `pending` 或 `processing`，v1 不增加单独的暂停打招呼状态；这些模块配置都与岗位发现运行无关。

因此，自动岗位鉴定关闭、自动打招呼关闭、当前鉴定策略异常缺失或固定招呼语尚未配置时，求职者仍可开始岗位发现。界面在开始前说明新岗位随后会停在哪个状态，但不把这些下游配置当作发现阻断条件；新岗位照常写入全局岗位池，没有有效 AI 结论的保持 `assessment_status=not_queued`，以后再由自动或手工操作入队。只有尚未手动保存任何在线简历版本，或 BOSS 会话等发现本身所需输入无效时才阻止开始；开始发现本身不会替用户刷新简历。

首次打招呼的自动入队还要区分本轮执行模式：`simulation` 只接收尚未模拟的 `not_queued` 岗位；`real` 同时接收 `not_queued` 和已经完成模拟的 `simulated` 岗位。模式在进入 `pending` 时冻结，配置变化只影响之后的新入队，不修改已经 `pending` 或 `processing` 的轮次。这样模拟可以作为真实打招呼前的演练，但不会消耗真实打招呼资格，也不会把一次已授权的模拟动作静默升级成真实动作。

自动模式从 `simulation` 改为 `real` 时，影响预览必须分别返回“现在可进入真实队列”和“仍在模拟、暂不进入”两个数量。后者只包括 `pending(simulation)` 与 `processing(simulation)`，不能被本次切换改成真实模式；它们先完成模拟，之后若自动真实打招呼仍开启，再作为新的 `simulated` 岗位重新检查并入队。该统计和筛选由 `AutomationSettings` 模块统一提供，Web 只展示返回结果和确认交互。

这些实例级开关、鉴定上限、自动打招呼模式、当前固定招呼语和真实打招呼时间窗统一保存在 SQLite 的单行 `automation_settings`，不属于岗位发现运行，也不在每个平台岗位上重复保存。`AutomationSettings` 模块负责校验和修改这一行，两个执行模块只读取；岗位入队时才把当时的模式和完整招呼语冻结到 `platform_jobs`。以后修改全局招呼语不改变已经排队或正在执行的岗位。这样界面或后台重启不会丢失设置，又不会把“以后如何自动入队”与“这个岗位当前执行到哪里”混成同一份状态。

求职者手工选择岗位时使用独立的“加入模拟队列”或“加入真实打招呼队列”命令，不复用或修改自动入队开关。真实命令需要对本批数量、招呼语和打招呼时间规则进行明确确认；确认后只是把选中的符合条件岗位加入 `pending(real)`。未设置时间窗时 `PostService` 可以全天领取，设置后才按时间窗领取。
