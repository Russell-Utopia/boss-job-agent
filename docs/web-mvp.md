# BOSS Job Agent MVP Web 交互规格

本文是 MVP Web 的实现与验收基线，记录 throwaway 原型已经验证并由求职者确认的用户可见行为。原型代码不是生产实现，也不应被复制成业务状态来源；领域术语以 [`CONTEXT.md`](../CONTEXT.md) 为准，持久化状态以 [`00001_initial.sql`](../internal/sqlite/migrations/00001_initial.sql) 为准，后台业务命令和状态所有权以 [`application-modules.md`](./application-modules.md) 为准。

已验证的原型源码固定保存在远端分支 `prototype/web-mvp` 的 `throwaway-prototypes/` 目录；该分支只作为交互证据，不合并进 `main`，生产实现仍以本文和上述权威文档为准。

## 1. MVP 界面边界

- MVP 只实现 Web，不同时维护 TUI。
- Web 只读取业务视图、提交业务命令，不直接访问 SQLite，也不管理 Worker 生命周期。
- 关闭 Web 不会停止岗位发现、岗位鉴定或打招呼，也不会清除已经持久化的运行、岗位、设置和正式策略版本。
- 策略优化页面会话是唯一例外：策略候选稿、生成样本选择和验收报告只存在于当前岗位鉴定页面，关闭或离开后永久消失。
- 不连接 BOSS、不会真实打招呼的 throwaway 原型只作为交互证据；生产 MVP 必须通过正式后台接口执行真实业务。

## 2. 信息架构

左侧导航固定按用户目的分为四个入口：

1. **岗位**：默认工作面，展示运行概况、全局岗位列表、筛选和单条或批量处理。
2. **岗位鉴定**：维护当前鉴定策略、生成策略候选稿和配置自动鉴定。
3. **打招呼**：配置自动打招呼、固定招呼语和真实打招呼时间窗。
4. **在线简历**：展示当前已保存版本，并提供唯一的手工刷新入口。

不设置独立的“执行情况”页面。岗位发现是一个可恢复运行，鉴定和打招呼是全局平台岗位上的状态，三者不能被包装成同一种任务或拆成三套岗位台账。

## 3. 岗位页

### 3.1 页首运行概况

页首依次展示“岗位发现、岗位鉴定、打招呼”三块概况：

- **岗位发现**展示搜索范围的已完成数与总数、当前岗位名、城市、页码、已发现岗位数和运行状态；当前运行可继续、暂停或提前结束。只有不存在未结束运行时才显示“创建岗位发现”。
- **岗位鉴定**展示已完成鉴定与当前仍未完成的数量，并提供“筛出未完成鉴定的岗位”。
- **打招呼**分别展示已打招呼和未打招呼数量，并提供筛出未打招呼和查看已打招呼的入口。

三块概况都使用“已完成 / 总数 + 进度条”的一致表达；概况中的“筛出”直接修改本页下方岗位列表，不跳转到另一套执行台账。

### 3.2 全局岗位列表

- 支持按岗位名或公司搜索，并按平台状态、AI 鉴定、人工结论、打招呼状态筛选。
- 普通列表列固定为“岗位、平台、AI 鉴定、人工结论、打招呼、操作”。不单独增加“为什么未打招呼”列；具体原因放在当前状态、禁用原因或岗位详情中。
- AI 鉴定与人工结论必须分列展示。人工列直接显示“未复核、已复核·适合、已复核·不适合、待重新复核”，不能要求用户从 AI 状态或操作资格反推是否复核过。
- 人工结论支持“已复核、未复核、人工适合、人工不适合、待重新复核”筛选。“建议人工确认”只是注意力筛选，不限制其他岗位的复核资格。
- 每个岗位行只提供“AI 鉴定、人工复核、真实打招呼”三类业务操作。可以执行时直接操作；不可执行时按钮禁用，并就近说明当前原因。
- 岗位分页允许每页 10、20、50、100 条，默认 10 条。改变筛选或每页条数后回到第一页并清除跨页勾选；每页条数和当前页写入 URL，使刷新后仍能还原当前列表位置。

### 3.3 批量处理

- 用户先选择“AI 鉴定、人工复核或真实打招呼”之一，再进入对应批量模式。
- 只有当前可以执行所选动作的岗位允许勾选；明显不可处理的岗位在提交前就禁用并展示原因。
- “全选”只选择当前页中对本动作可选的岗位，不跨页隐式选中。
- 提交时后台仍逐项重新校验，避免页面打开后状态变化；结果明确展示成功数量和因状态变化被跳过的岗位及原因。
- 批量操作只是一轮交互，不建立批次业务表或批次历史。

## 4. 岗位发现交互

- 尚未保存在线简历版本时，“创建岗位发现”禁用，并引导用户先到“在线简历”页手工刷新。
- 创建确认页展示本轮实际采用的在线简历版本和全部搜索范围。自动鉴定关闭、自动打招呼关闭或固定招呼语未配置只作为下游提示，不阻止开始发现。
- 一轮发现固定使用创建时记录的在线简历版本；暂停、恢复或 Web 重开都不能切换版本。运行中刷新得到 v2 时，界面同时说明“当前已保存 v2；本轮仍使用 v1；v2 用于下一次发现和尚未开始的鉴定”。
- 新发现运行使用新简历版本只表示搜索范围采用新版本，不触发历史岗位批量 AI 鉴定。
- 同一稳定 `platform_job_id` 再次出现时只更新同一全局岗位；JD 判断内容未变化就保留现有鉴定和打招呼状态。同一公司发布相似 JD 但获得新的 `platform_job_id` 时展示为新岗位，不继承旧岗位结论。

## 5. 人工复核交互

- AI 为“适合、不适合、待用户确认”或尚无 AI 结论的岗位都允许人工复核；已有人工结论也允许再次复核。
- 复核弹窗同时展示当前 JD 的岗位名称、公司、城市、薪资、完整工作职责和任职要求，以及 AI 结论、理由、实际采用的版本和当前人工结论。
- “适合、不适合”操作固定在弹窗底部，要求用户以当前完整 JD 为依据，不能只依据 AI 摘要判断。
- 保存人工复核只更新岗位的全局人工结论，整个过程调用 LLM **0 次**，也不自动生成或修改鉴定策略。
- 与当前 JD 一致的人工结论优先于 AI；JD 判断内容变化后旧人工结论继续展示为“待重新复核”，重新复核前不参与当前判断。

## 6. 岗位鉴定页与策略候选稿

### 6.1 当前策略与自动鉴定

- 页面直接展示当前启用的完整鉴定策略；新实例已有“默认策略 v1”。
- 自动岗位鉴定开关只控制新的合格岗位是否自动安排鉴定，关闭不取消已经等待或正在执行的工作。
- 配置项名称使用“AI 同时鉴定数”，输入必须是正整数。5 只是首次默认值，不是最大值；调低数值不打断已经开始的鉴定。

### 6.2 策略优化

- 人工复核期间不调用 LLM。只有用户主动点击“生成候选策略”时才调用模型一次；“重新鉴定”不再作为单条或批量岗位操作。
- “岗位鉴定”页内提供“策略优化”区域或 Tab，不新增左侧一级导航。页面列出当时仍对应当前 JD 的全部人工“适合”和“不适合”复核；不要求岗位已有 AI 结论，也不因 AI 使用旧策略、AI 与人一致或 AI 判为不适合而排除。
- 每次生成前提供临时选项“同时验收候选策略（会产生额外模型调用）”，默认关闭且不保存为自动化设置。关闭时，生成调用使用当前完整策略和全部有效人工复核，不划分样本，也不执行验收。
- 开启策略验收时，系统默认随机勾选约 50% 的有效人工复核，求职者可以在生成前手工调整；最终勾选集合与当前已保存的完整在线简历、当前完整策略共同作为生成输入。全部有效人工复核构成验收集合，因此生成集合是验收集合的子集；不自动做类别平衡、相似岗位归组或其他统计抽样。
- 生成前和候选稿弹窗都明确提示：结果只依据此时此刻的信息；关闭后无法恢复；以后重新生成会使用届时的策略和人工标注，并再次调用模型。
- 一次调用返回一份完整、可编辑、可直接采用的唯一候选稿，不返回需要用户拼接的零碎建议。
- 当前策略与候选稿使用浏览器本地、确定性的逐行差异展示：删除为红色，新增为绿色，未变化内容弱化。差异计算不调用模型，也不展示额外的模型式“主要变化”摘要；编辑候选稿时差异实时更新。
- 用户编辑模型文本仍然表示利用了模型结果；编辑后的整份文本继续是本次候选稿。
- 关闭、取消、离开岗位鉴定页，或在已有候选稿时重新生成，都先展示醒目的二次确认，明确说明未采用内容会永久丢失且无法恢复。确认后只丢弃页面内存，不调用后台删除接口。
- 重新打开页面、浏览器崩溃、Web 进程退出或后台重启后都不能恢复候选稿。下次生成重新读取届时的信息，不复用旧候选稿。
- 只有点击“采用此策略”才把当前完整文本创建并启用为新的不可变正式策略版本；不新增候选稿表、候选稿字段、采用/放弃历史或服务端采用/放弃草稿接口。

### 6.3 可选策略验收

- 策略验收只在生成候选稿前显式开启；未开启时页面标明“本候选策略未经独立验收”。候选稿已经使用全部有效人工复核生成后，不能再为同一候选稿补开验收；切换模式必须重新生成。
- 验收通过额外模型调用，使用生成时记录的同一在线简历版本，分别用当时的当前策略和候选策略处理验收时的全部有效人工复核，只产生本次交互中的比较证据。报告同时展示全量结果，以及未参与生成的记录结果，帮助识别依赖固定词汇、公司名或具体案例的取巧策略；任一生成样本已经因 JD 或人工结论变化而失效时，必须重新生成。
- 验收依次比较“人工不适合、AI 判适合”“人工适合、AI 判不适合”“AI 要求人工确认”。前两类错误都不增加，且至少一类减少时为“验收通过”；前两类不变但人工确认减少时也可通过。一项改善而另一项退步时显示“结果有取舍，需要人工判断”；样本不足时显示“证据不足”。
- 验收结果不会写回任何平台岗位，不改变当前 AI 结论、鉴定版本、鉴定队列、岗位当前判断或打招呼资格。未通过、结果有取舍、证据不足或未执行验收时，求职者仍可明确选择人工采用。
- 验收针对候选稿当前完整文本；验收后再次编辑会立即使旧报告失效。可以重新验收或直接人工采用，但任何结果都不会自动采用策略。
- 生成样本选择和验收报告与策略候选稿一样只存在于当前页面会话；关闭、取消、离开或重新生成后永久消失，不建立验收历史。采用候选稿只创建正式策略版本，新策略供以后真正开始的 AI 鉴定使用，不扫描或改写已有成功鉴定。

## 7. 打招呼页

- 自动打招呼开关只控制新的合格岗位是否自动入队；关闭不撤回已经等待或正在处理的工作。
- 产品只提供真实打招呼，不提供模拟打招呼、执行模式选择或模拟完成状态。受控测试 Adapter 和本地 live integration test 不出现在产品页面或岗位状态中。
- 开启自动打招呼前，影响预览展示当前会进入真实打招呼队列的岗位数量、完整固定招呼语和当前时间规则；确认后只授权之后新符合条件的岗位，不修改已有队列。
- 固定招呼语在岗位入队时冻结；修改全局文本不改变已经等待或正在执行的岗位。
- 手工真实打招呼必须再次确认本批岗位数、完整招呼语和当前时间规则；只授权本批岗位，不修改自动开关。
- 真实打招呼时间窗为空时明确显示“全天可打招呼”。添加时间窗使用弹窗，可直接选择上午 09:00–12:00、下午 14:00–18:00、晚间 19:00–21:00，也可通过起止时间控件自定义并保存多个互不重叠区间。

## 8. 在线简历页

- “刷新在线简历”是产品唯一访问 BOSS 更新求职资料的入口，必须由用户显式触发。
- 刷新成功且内容变化时新增递增版本；内容未变化时保留原版本号；读取失败时保留最后一次可靠版本并展示错误。
- 页面展示用户可理解的版本号、保存时间和对当前发现运行的影响，不展示内部数据库 ID。

## 9. 首次初始化

- 在线简历版本：无，必须先手工刷新。
- 当前鉴定策略：默认策略 v1。
- 自动岗位鉴定：关闭。
- AI 同时鉴定数：5，仅为默认值。
- 自动打招呼：关闭。
- 固定招呼语：未配置。
- 真实打招呼时间：全天。

## 10. 用户可见状态用语

Web 不直接暴露调度实现词：

| 内部状态 | Web 用语 |
| --- | --- |
| `not_queued` | 尚未安排 |
| `pending` | 待鉴定 / 等待真实打招呼 |
| `processing` | 鉴定中 / 打招呼中 |
| `needs_user_confirmation` | 需要人工确认 |
| `possibly_contacted` | 可能已打招呼，正在核对 |
| `human_reviewed_jd_hash <> jd_hash` | 待重新复核 |

界面不能让用户通过内部状态组合自行推断“能不能操作”；每个动作必须直接返回可执行性及其用户可见原因。

## 11. MVP 验收场景

实现至少验证以下交互：

1. 首次没有在线简历时无法创建岗位发现；刷新成功、未变化和失败分别得到正确结果。
2. 使用 v1 的发现运行中刷新得到 v2，当前运行保持 v1，尚未开始的鉴定采用 v2。
3. 相同 `platform_job_id` 重复发现不产生第二条岗位；新 ID 的相似 JD 产生独立岗位。
4. 岗位列表切换 10 / 20 / 50 / 100 条、筛选、翻页和刷新 URL 后结果一致，不保留无效跨页选择。
5. AI“不适合”的岗位仍可人工复核；连续人工复核期间没有模型调用。
6. 默认关闭策略验收时，生成策略只调用模型一次；本地差异计算和编辑不增加调用，候选稿标明未经独立验收。
7. 开启策略验收时可以在生成前调整默认随机勾选的生成样本；全量与未参与生成结果、验收结论、编辑后失效和额外模型调用都符合第 6 节。
8. 候选稿关闭告警并丢失、重新进入无恢复、编辑后采用、增加人工标注后重新生成都符合第 6 节。
9. 不可处理岗位在选择前禁用且说明原因；提交瞬间状态变化时后台跳过并返回原因。
10. Web 关闭后持久化运行和队列继续，重新打开可恢复；策略候选稿、生成样本选择和验收报告不会恢复。
11. 自动和手工真实打招呼确认展示影响数量、完整招呼语和“全天”或具体时间窗；未确认时不产生真实外部动作。

## 12. 已确认的边界

MVP 不提供模拟打招呼。原先用来防止未验证编排意外发送的 Simulation 已由受控 Adapter、生产 Adapter 的显式本地 live integration test 和完整真实链路测试取代；测试能力不形成 Web 入口、自动化设置或岗位业务状态。具体理由与测试边界见 ADR-0024。
